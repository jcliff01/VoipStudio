Getting started

What VoipStudio is

VoipStudio in one paragraph

VoipStudio reads packet captures (.pcap / .pcapng / .cap) of VoIP traffic and turns them into calls you can read: who called whom, whether the call connected, how the audio sounded, and where anything went wrong. It reassembles SIP signaling and RTP audio the way Wireshark does, then goes further — it groups the many SIP dialogs of a call that crosses a gateway into ONE call, estimates voice quality (MOS), separates real packet loss from hold-music gaps, decodes and plays the audio, and charts trends across thousands of calls.

It is built for a voice engineer chasing a specific complaint ("this call sounded choppy") and for capacity/quality trend work across a whole capture.

The shape of the app

  • A toolbar across the top: open captures, search, export, settings, help.
  • A row of TABS, each a different lens on the same analyzed capture. Start at the Dashboard, drill into Calls, open a call to see its ladder/audio/SIP, and use Graphs and Endpoints to see the big picture.
  • Everything shares one analysis. Filtering the Packets tab, opening a call, or charting a metric all read the same in-memory model.

First things to try

  • Open a capture folder (toolbar → Open Folder). VoipStudio analyzes every capture in it and lands you on the Dashboard. A folder bigger than this PC can hold at once opens in groups you page through (see "Capture groups" in this section).
  • Double-click any call to open its detail window (ladder diagram, audio player, SIP log, per-packet view).
  • Hover any column header — every column has a plain-language definition tooltip.
  • Press F1 on any tab for help about THAT tab.

Tip: nothing you do in VoipStudio changes your capture files. It is read-only analysis — explore freely.

Privacy mode (toolbar)

The Privacy toggle masks every identifying value on the OPEN capture — phone numbers, display names, IP addresses, hostnames, carrier/org names, DTMF digits — with random but CONSISTENT fakes drawn from built-in name/word libraries, so call flows stay structurally valid for screenshots and demos. The consistency rules keep flows readable: the same real number becomes the same fake everywhere (including inside raw SIP text), numbers that share trailing digits still share them, and a /24 stays one /24 (private space stays private, the lab range stays lab).

Display-only: the capture files are never modified — turning privacy off re-analyzes and restores the truth. While masked, everything that re-reads the RAW files is disabled, because those bytes still hold the real data: audio playback, WAV export, DTMF audio scans, and evidence packages. The Packets grid and the HTTP full-message dialog also decode raw bytes — avoid screenshotting those two in privacy mode.

Loading captures

Ways to load a capture

  • Open Folder… — analyzes EVERY .pcap/.pcapng/.cap in the folder as one session. This is the normal path for a ring-buffer capture split into hundreds of files.
  • Open Files… — pick one or more specific capture files.
  • Drag and drop files or a folder onto the window.
  • Command line — pass file or folder paths when launching; they analyze on startup.

What happens on load

VoipStudio reads the files in timestamp order, dedups SPAN mirror copies (see Settings), classifies every packet, reassembles SIP dialogs and RTP streams, correlates the dialogs into calls, and computes quality metrics. A progress bar in the toolbar tracks it; large multi-gigabyte sessions take a little while, and analysis runs off the UI thread so the window stays responsive.

Multi-file sessions

Files are treated as one continuous capture, so a call whose packets straddle two files is still assembled correctly. The title bar shows the folder (or the file, or a "+N more folders" summary). Each row's Files/File column tells you which capture a given call or packet actually lives in, so you can jump to it in Wireshark.

A call cut off at the very start or end of the capture window may show a blank End or missing setup — that is the ring-buffer edge, not a fault in the call.

Capture groups (more than fits in memory)

What it is

A capture bigger than this PC can analyze at once opens in GROUPS: consecutive slices of the file set, in time order, each small enough for the machine. A bar appears under the toolbar — "Group 2 of 4 — files 201–400 of 800" — with Previous / Next buttons (Ctrl+PageUp / Ctrl+PageDown) that analyze the neighbouring slice. Everything on every tab is about the group on screen.

How the size is chosen

What limits a machine is memory at the PEAK of the scan: every file's RTP packet data has to exist until the analysis groups it into streams, and that is about a third of the capture's size in RAM (measured: 0.36 bytes of heap per byte of capture). VoipStudio refuses to go past 45% of the PC's RAM, so a set whose estimate fits that ceiling opens as ONE analysis, exactly as before; a bigger set is cut so that each group fits with a little to spare. On a 16 GB PC that is roughly 18 GB of capture per group — about 190 of the 95 MB ring files a CUBE writes; a 64 GB PC holds four times as much.

If a group still runs out (the estimate is a rule of thumb; a capture with unusual traffic can cost more per byte), the analysis stops itself, learns the real cost from how far it got, cuts the set smaller and goes again — you see it in the status line.

The time bar (jump to any moment)

Under the buttons is a scrubber drawn on the capture's real TIME, read from the files themselves — not on file numbers. That distinction is the point: ring files are a fixed SIZE, so a busy ten minutes fills three of them while a quiet hour fills one, and "group 4 of 9" tells you nothing about when it is. On this bar the file boundaries are tick marks, so where they crowd together the capture was busy.

  • Drag the blue band to move the analyzed window somewhere else in the day.
  • Drag its edges to make the window wider or narrower. It stops at what this PC's memory allows and says so.
  • Click anywhere on the track to jump the window there, keeping its width.
  • The line underneath always names both: the from/to of what you are looking at, and the from/to of the whole set.

Wherever you drop it, that slice becomes a group in its own right — Previous and Next keep working either side of it — and the analysis of that slice starts as soon as you let go. Hovering a spot names the file that was being written then.

Files per group

The box in the bar shows the size the PC was given; type a smaller number and press Enter to re-cut the whole set — you stay on the group holding the file you were looking at. Smaller groups use less memory and show less of the day at once. The file picker (Open Folder) also says how many of the folder's files this PC can take in one go.

What a group edge does to a call

A call that crosses a group boundary appears in BOTH groups, each seeing only its part — exactly like a call at the edge of a ring-buffer capture: the SIP log's capture-edge notes say when the start or the end of a call was not in the slice. There is no overlap between groups. When one call matters, open the two groups around it, or pick a file range in the Open Folder dialog centred on it.

On the command line

`vsx analyze <folder> --group list` prints how the machine would cut the folder; `--group K` analyzes group K (with `--group-size N` to cut by a fixed count instead of by memory), and the CSV exports then cover that group.

Searching & filtering calls

The Find calls box

The toolbar search box filters the Calls tab live. Type plain text or a query expression and press Enter. Your recent searches are remembered (dropdown / history).

Plain text

Matches across caller and callee numbers, display names, SIP and MEDIA IP addresses (and their resolved host/carrier names), and Call-IDs. So a carrier media IP that never appears in the signaling columns will still find its calls.

Query operators

Combine these (space-separated terms all have to match):

  • loss>2 — worst capture loss above 2% (also loss<, >=, etc.)
  • jitter>30 — worst jitter above 30 ms
  • mos<3.5 — minimum MOS below 3.5
  • state:failed — by call state (failed, completed, cancelled, answered, ringing…)
  • divergent — only calls where RTP and RTCP disagree about loss
  • Numbers, IPs and names not preceded by a keyword are treated as plain text.

Subnets and addresses

Type a subnet the way you would write it in a router config:

  • 10.90.216.0/22 — anything with an address inside that subnet, on either end
  • src:10.90.216.0/22 — only when the SENDING end is inside (dst: for the receiving end)
  • !10.90.216.0/22 (or -10.90.216.0/22) — nothing inside that subnet is involved
  • src:10.90.216.5 — with src: or dst: in front, a plain address means exactly that host
  • 10.90.216.5/32 — the same host on either end

They combine with each other and with everything above: "10.90.216.0/22 mos<3.5" is the bad-sounding calls at one site, and "src:10.90.216.0/22 !dst:10.90.216.0/22" is audio leaving it. IPv6 prefixes (2001:db8::/32) work the same way.

A CALL counts as inside when any of its legs' SIP addresses OR any of its media addresses is. Both matter: behind a CUBE a phone never appears in the SIP the capture sees — only in the negotiated media — so a search on signalling alone would miss every one of that site's calls.

A plain address with no "/" is still ordinary text, exactly as before: it finds anything CONTAINING those characters. That is a text match, not a subnet — "10.90.21" finds 10.90.21.x but also every 10.90.210-219.x and 110.90.21.x. Add the prefix length when you mean the network.

If a subnet is malformed ("10.90.216.0/33") the search is not applied and the status bar says why, rather than quietly showing every row or none.

The same syntax works in the Legs, DTMF, RTP Streams, SIP Messages, Endpoints and HTTP search boxes, the Packets tab's Address box, the Graphs tab's Subnet box, and on the command line as vsx analyze --subnet. The Packets tab's display filter also takes ip.addr == 10.90.216.0/22, Wireshark-style.

Related filters elsewhere

  • Bad Calls tab has its own symptom/cause checkboxes (see its help).
  • Right-clicking a call, stream, endpoint or packet offers "Filter … to this …" actions that cross-navigate between tabs (e.g. filter the Packets tab to one stream).
  • The Packets tab has a Wireshark-style display-filter box of its own.

Tip: sort any grid by clicking its column header; click again to reverse. Sorting by Audible Loss %, Poor Audio s, or Min MOS is the fastest way to the genuinely bad calls.

Names, carriers & time zones

Making addresses readable

Raw captures are full of bare IP addresses. VoipStudio can resolve them three ways, all optional and all set in Settings:

  • Hosts file import — a plain "ip hostname" per line file (# for comments). The most reliable naming; applied live and re-applied after every analysis. Use this to label your gateways, SBCs, agents, and lab gear.
  • Reverse DNS (rDNS / PTR) — asks your DNS server for names of LAN/private IPs. Cached to disk. Good when your internal DNS has PTR records.
  • Whois (RDAP) — looks up the owning carrier/organization of PUBLIC IP blocks. Needs internet, cached to disk permanently. This is what fills the carrier/org columns and tells you which carrier a public endpoint belongs to.

Once resolved, names appear everywhere — grids, ladder diagrams, graphs, exports — and searching by name works.

Time zones

Captures are stored in UTC. The display time zone (Settings) changes how EVERY timestamp in the app is shown; daylight saving is handled automatically for the chosen zone. The zone abbreviation appears next to full timestamps so there is never any doubt which zone you are reading.

Nothing here modifies the capture — resolution and time zone are display conveniences layered on top of the immutable packet data.

Dashboard tab

What it is

The landing page: a one-screen health summary of the whole capture. Read it first to decide where to dig.

What it shows

  • Headline totals — how many calls, streams, packets, and files; the capture's time span.
  • Call outcome mix — how many completed, failed, cancelled, unanswered.
  • Quality summary — how many calls have poor audio, high loss, high jitter, or low MOS.
  • An ATTENTION list of the streams/calls most worth opening — the worst offenders, each shown by its Id. Selecting one is a shortcut into the detail.

How to use it

Treat the Dashboard as triage. If the outcome mix or quality summary looks wrong, jump to the Calls or Bad Calls tab and sort by the relevant column. If a specific stream is called out in the Attention list, open it directly.

Every number here is derived from the same analysis behind the other tabs — the Dashboard just aggregates it. Nothing is estimated differently.

The tabs

Calls tab

What it is

The heart of the app: one row per CORRELATED call — meaning all the SIP dialogs (legs) of a call that crossed a gateway/B2BUA are joined into a single logical call. A call through a CUBE with an inbound and outbound leg is ONE row here, not two.

Reading a row

Columns cover identity (caller/ANI, callee/DNIS, display name, asserted identities), outcome (State, End Reason, Cause), setup timing (INVITE→100/18x/final, 200→ACK), and quality (Min MOS, Worst/Audible Loss %, Loss Bursts, L Events, Worst Jitter, Poor Audio s, Worst leg imperfect %, and what the receivers' RTCP reports say: RTCP lost, Worst RTCP loss %).

Hover ANY column header for its full definition — every column is documented there, and the same definitions appear when you hover an entry in the column chooser (right-click any header), which is where you go to decide whether to switch a column ON.

Rows are TINTED so the calls worth opening stand out while you scroll: pale red = choppy audio or a failure cause worth explaining, pale amber = the call failed one or more times before it worked (the Fails before success column). A 404 or a busy is not coloured — those are ordinary outcomes, and colouring them would paint half a contact-centre capture red. The red level uses exactly the Bad Calls tab's definition, so a red row here is a row that tab would list.

The Asserted calling ID and Asserted called ID columns name the two SIDES of the call as the network finally asserted them. Neither can ever show the other side's party: a hub that words its re-INVITE from its own viewpoint asserts the customer back as its "called" party, and taken literally that filled both columns with the same person.

Working the tab

  • Double-click a row to open the call detail window (ladder, audio, SIP log, packets).
  • Right-click → "Export incident report (HTML)…" writes a self-contained, shareable HTML document for that call (summary, identity, setup timing, per-stream quality, the plain-English diagnosis, and the SIP ladder image) — it prints cleanly to PDF from a browser. The same button is on the call window's Report tab.
  • Sort by a quality column (click the header) to rank calls; Audible Loss % and Poor Audio s surface the calls a caller actually complained about, while raw Worst Loss % also counts hold/MOH gaps.
  • To find calls whose audio really broke up without wading through hold music and one-way legs, sort by L Events or Worst leg imperfect %. L Events counts how many times the audio went missing and came back (one long hold gap is ONE event; choppy audio is dozens). Worst leg imperfect % is the share of audio seconds with a dropout on the call's worst leg, direction and device, with silence not counted as audio — so a short agent leg that broke up inside a long IVR call still stands out. It is TIME, not loss: steady single-packet loss of about 3% can touch 85% of the seconds, and both numbers are right. It stays blank for attempts that never connected and for anything with under 10 seconds of audio, so short failed calls do not crowd the top of the sort. The Settings "loss event minimum" sets how many lost packets in a row make one event (default 1).
  • Use the toolbar Find box to filter (see "Searching & filtering").
  • Right-click for actions: open detail, open several selected calls side by side, open the combined view of a call plus its related calls, jump to the SIP flow, find/combine related legs, filter the SIP or Packets tab to this call, copy identifiers or a Wireshark filter.

Correlation

The Correlated By column tells you HOW the legs were joined (Session-ID, Replaces transfer, B2BUA time-window chaining, or a rare-number tie). See "How calls are correlated" under Concepts for the full story and the tolerances that control it.

Legs tab

Legs tab

One row per SIP dialog, rather than per call. A call through a B2BUA is at least two legs (the inbound one and the one the B2BUA placed onward), and a contact-centre call is often four or five: carrier to CUBE, CUBE to CVP, CVP back for the agent, and so on.

Use it when the CALLS tab has rolled something up and you need to see the hops: which leg carried the audio, which one failed, which one the agent actually answered.

  • "Group by call" (on by default) keeps a call's legs adjacent and shows the WHOLE call when any one of its legs matches your search. Turn it off for a plain chronological list you can sort by any column.
  • The Calls tab's "Legs" column jumps here already filtered to that call.
  • Search matches caller, callee, display names, Remote-Party-ID, P-Asserted-Identity, Handled By, Call-ID and both addresses. "call:N" filters to one call, "state:x" to a leg state.
  • Double-click any row to open the call window.

The audio columns

The right-hand block is per DIRECTION, and the arrows are relative to THIS LEG:

  • → is media the leg's CALLER side SENT.
  • ← is media sent back to them.

Which stream belongs to which direction is decided from the SDP media endpoints, falling back to the SIP addresses when the leg's own SDP was never captured. Hover any column header for its full definition.

Two of them are worth knowing before you read the numbers:

  • "Loss" already excludes packets inside gaps the call EXPLAINS — a hold, a signalled media re-route, or a carrier suppressing silence. Those packets were never sent, so counting them made every VAD trunk look broken. The raw figure is still on the RTP Streams tab as "Loss % (capture)".
  • "RTCP loss" and "RTCP lost" can be BLANK. Blank means no in-window figure could be derived from the receiver's reports — it does NOT mean clean. See the header tooltip.
  • "L events" count how many times the audio went missing and came back, and "Imperfect audio %" is the share of that direction's seconds with a dropout in them, long gaps (hold, one-way stretches, dead air) left out. The Calls tab's "Worst leg imperfect %" takes the worst of a call's legs, scoring each device on a leg separately — so a leg re-pointed from one phone to another mid-call can read higher there than in this tab.

Joined By

Says which correlation rule first tied this leg to its call — Session-ID, Replaces, a B2BUA chain, a hub re-connect, and so on. Search for a rule name ("B2BUA") to audit every heuristic join in the capture. Protocol-asserted ties (Session-ID, Replaces) are proof; everything else is a heuristic worth checking when a call surprises you. "How calls are correlated" under Concepts has the full ladder.

DTMF tab

DTMF tab

One row per call that carried any digits, so you can answer "what did the caller key in" without opening calls one at a time. Sort, search and column-choose like the other grids; double-click opens the call.

The two digit columns are deliberately separate

  • "Digits" are the ones carried in the MEDIA — RFC 4733 telephone-event packets.
  • "INFO digits" are the ones carried in SIGNALLING — SIP INFO bodies (application/dtmf-relay, application/dtmf) or KPML.

They are NOT merged, because a B2BUA that converts RFC 2833 to SIP INFO carries the SAME keypress both ways: merging would print every digit twice. "Method" names whichever was seen. When a call had no media digits at all, the signalling ones are used for the summary so the row is still useful.

Reading the digit string

A space appears wherever the real silence between two keypresses ran longer than five seconds, measured end-to-start. That is usually the boundary between separate entries, so "12031976 12031976" means the IVR rejected the value the first time and the caller keyed it again. The underlying string is unspaced, and search ignores spacing on both sides — paste a value straight out of the grid and it will match.

One keypress heard on several streams (the caller's leg and the relayed copy) is collapsed to one digit. A genuinely repeated key on ONE stream is kept: "99" stays "99".

Stream Explorer

Stream Explorer

An audit view over MANY conversations at once, in the call window's audio language. Open it by right-clicking a waveform in a call window's Audio tab, or from the RTP Streams grid's context menu.

Two entry points, answering two different questions:

  • "Every RTP stream live at THIS instant" — did the neighbours suffer when this call did? A loss spike that hits one call is that call's problem; one that hits everything at the same second is the network's.
  • "All audio to/from THIS address for the whole capture" — is this phone always bad, or was it bad once?

What you see before anything is decoded

Decoding is per-conversation and LAZY, and that is deliberate: one 100 MB ring file can hold several hundred conversations, and decoding them all up front would be gigabytes of audio nobody asked to hear.

Until you click a conversation its lanes show a hatched placeholder band — but the REAL loss and jitter overlay and the anomaly badges are already drawn on it. That is what answers "did this one have problems" without decoding anything.

Clicking a conversation decodes and solos it, and its group header is marked "NOW PLAYING". Only a handful of conversations keep their decoded audio; older ones are released, and their lanes go back to saying "audio not loaded".

Things worth knowing

  • A click on a MUTED lane's waveform SELECTS that conversation rather than seeking. Without that, clicking a row in a list of hundreds silently scrubbed whichever other conversation happened to be unmuted.
  • "Zoom to the one I pick" (on by default) fits the view to the conversation you clicked. On a whole-capture time axis a three-second call is a few pixels wide next to a twelve-minute one.
  • An empty wave box has three meanings and the lane always says which: not decoded yet, this lane's media is elsewhere on the time axis (it names where), or the wire really did carry silence.
  • Lanes are drawn by the same code as the call window's Audio tab, on purpose — so "the gap I saw on the call" and "the gap I saw in the audit" stay comparable.

Back to back (no idle time)

With this ticked the conversations are laid end to end and the silence between them is squeezed out of the axis: an endpoint with eleven calls spread over two hours reads as a few minutes of audio you can scroll and listen through in one pass. Nothing inside a conversation moves — every gap, badge and RTCP mark keeps its place against its own audio — and the clock row on the axis still shows the REAL time of whatever is under the cursor, so it jumps at each boundary.

Opened from the Endpoints tab (right-click → View all audio from this endpoint) it starts packed and shows the audio that endpoint SENT — what everyone else heard from it; the combo beside the checkbox switches to the audio it was sent, or to both directions. Packing lays conversations out one after another, so for a gateway carrying hundreds of calls AT ONCE the packed axis is longer than the capture itself — untick it there.

Bad Calls tab

What it is

A filtered Calls view showing only the calls worth opening, in TWO panes — because "this call failed" and "this call sounded bad" are two different investigations and one mixed list means scrolling past a hundred 503s to find broken audio.

  • The TOP pane lists calls matched by a ticked DISCONNECT CAUSE, with the cause and the identity columns on and the audio-quality columns off — a call that never connected has no audio to rate.
  • The BOTTOM pane lists calls matched by a ticked AUDIO SYMPTOM, with the quality columns on and the cause column off.

Each pane sorts, right-clicks and chooses its own columns independently (right-click any header), and each carries its own count in its title. Drag the divider to give one pane more room. A call that BOTH failed and broke up appears in both panes — each one is answering a different question about it — and Export All writes it once, carrying both reasons.

Symptoms vs causes

  • Symptoms are what the listener/PBX experienced: choppy audio (audible loss over the threshold), high jitter, low MOS, one-way audio, dead air, RTP-vs-RTCP divergence, setup failures, and so on.
  • Causes are contributing conditions the analysis can name.

Tick the symptom checkboxes to define "bad" for your purpose; the list updates to match. Your checkbox selection is remembered between captures and sessions, so the tab stays tuned to what you care about.

What starts ticked

Everything that describes audio somebody heard break up. Four symptoms start UNticked because they describe the media PATH or a disagreement between two vantage points rather than a complaint: "RTCP loss / capture clean" (the far end counted loss this capture can prove did not happen — most often a media source renumbering its RTP sequence), "Stream resets" (a prompt replay or a media re-anchor), "One-way audio" (whole architectures are one-way by design) and "Loss is one long gap" (hold or music-on-hold). Tick any of them when that is what you are hunting.

On the causes side, every SIP failure status and Q.850 cause starts ticked EXCEPT the ones that are ordinary call outcomes rather than faults: normal clearing, user busy, and not-found / unallocated number — dialing a number that does not exist is a dialing mistake, and on a contact-centre capture it is the single commonest failure there is.

Tuning the thresholds

CHOPPY AUDIO takes two numbers, both in Settings, and needs BOTH: what share of the stream's audio SECONDS had a dropout in them (default 25%), and how much of it really went missing (default 3% actual loss, hold/MOH and silence-suppression gaps excluded). Two, because either alone lies — a steady 3% loss touching 80% of the seconds is broken audio, the same 3% inside two seconds is one blip, and 80% of the seconds touched at 0.1% loss is a codec dropping the odd packet. Read together they are the summary: "80% of the call had 3.5% audio loss".

The other floors — jitter, MOS, loss bursts, the raw-loss symptom — are in Settings too. If this tab flags too much or too little, adjust those; see the Settings help.

Using it

Same row format and right-click actions as the Calls tab. Sort by Imperfect audio % (how much of the conversation had a dropout in it) or Poor Audio s to rank the genuinely painful calls first — Worst leg imperfect % beside it reads the worst single lane instead, which is how a short bad agent leg inside a long IVR call shows up. Then double-click to open and confirm in the audio player and ladder. The Asserted calling/called ID columns show the FINAL asserted identity (RPID/P-Asserted-Identity) when it differs from the bare number — who was actually connected at the end, e.g. the agent an inbound call was delivered to.

Exporting the evidence

  • Export All… writes a monitor-style package for EVERY displayed call in BOTH panes: the call's pcap, WAVs, SIP log, a problem report headed by why it was flagged, and a badcalls.jsonl index — exactly what live monitoring would have preserved.
  • Export Selected… does the same for just the highlighted rows (Ctrl/Shift-click to pick several). Clicking into one pane clears the other's selection, so what you export is always what you are looking at.

RTP Streams tab

What it is

One row per RTP media stream — each direction of audio is its own stream, so a normal two-way call contributes two rows here. A stream with a blank Call means no SIP setup was captured for that media (see its Notes).

Finding streams

The "Find streams" box at the top narrows the list. Words combine — a stream has to match all of them:

  • 10.90.216.0/22 — either end of the stream is in the subnet; src: / dst: for one end; ! to exclude
  • call:12 — the streams of one call
  • loss>2, jitter>30, mos<3.5 — quality thresholds
  • anything else — matched as text against the addresses and their names, codec, SSRC, side and notes

A stream is judged by its OWN two addresses, so "dst:10.90.216.0/22" is the audio the site received and "src:10.90.216.0/22" is the audio it sent. Filtering rebuilds the list in capture order; click a column header to sort the result. See "Searching & filtering" for the full syntax.

What each row tells you

Source/destination ip:port, SSRC, codec (with a lock symbol for SRTP), packet count, capture-observed Loss %, Loss Bursts, L events, Audible Loss %, Imperfect audio %, mean Jitter, estimated MOS, and the RTCP receiver's own numbers (cumulative lost, fraction lost) plus the RTP-vs-RTCP divergence verdict. Hover any header for the full definition.

The most useful columns

  • Loss Bursts is the quick real-vs-math discriminator: ONE burst is usually a single continuous gap (hold/MOH or a media re-route while sequence numbers kept counting); DOZENS of bursts is audio that actually broke up.
  • L events is the same idea with sender silence suppression left out and the Settings "loss event minimum" applied (default 1 lost packet).
  • Imperfect audio % is the share of the stream's audio seconds (seconds in which packets arrived) that had a dropout in them — TIME affected, not packets lost. Silence is not audio time and a long gap is never a dropout second, so it separates steady break-ups from one long hold gap.
  • Audible Loss % excludes long gaps, so it is the loss a listener really heard.
  • Dropout loss % is how HARD the audio was breaking up while it was breaking up: the packets lost inside the dropouts, over what those seconds should have carried. Only seconds that had a dropout AND packets arriving count, so audio that simply never came — a one-way stretch, hold, dead air — cannot reach it and it never reads 100%. Read it WITH Imperfect audio % beside it: that says how MUCH of the audio was affected, this says how BAD it was where it was. A phone dropping a packet a second is ~85% imperfect and a few % here; a line that tore for four seconds inside a good call is a few % imperfect and 50%+ here. Neither number finds the other one's case on its own.
  • Start is in the display time zone picked on the toolbar. Two more readings sit in the column chooser (right-click a header): Start (UTC), the raw capture timestamp to quote to a carrier whose logs are UTC, and Date, which an HH:mm:ss column cannot give you when the capture crosses midnight or a group of files covers two days.
  • RTP vs RTCP stats tells you WHERE loss happened relative to the capture point (downstream, upstream, or a SPAN gap). See "Packet loss explained" under Concepts.

Codecs it can play

VoipStudio natively decodes G.711 (µ/A-law), G.722, G.726, G.729, GSM, Opus and L16. For codecs it has no native decoder for — iLBC, G.723.1, AMR-NB and AMR-WB — it uses an ffmpeg binary if one is installed on the machine (found on PATH or a standard install location); the player then labels the audio "(via ffmpeg)". Without ffmpeg those streams stay stats-only (everything except playback still works). Set the VSX_FFMPEG environment variable to point at a specific ffmpeg if needed.

Actions (right-click)

Open the owning call detail; play this stream plus its reverse direction in the audio player; scan for in-band DTMF; simulate a jitter buffer (see below); open the SIP flow; filter the Packets tab to just this stream; export the stream to WAV or its packet timing to CSV; copy ip:port, SSRC, or a Wireshark filter.

Simulating a jitter buffer (playout)

"Simulate jitter buffer (playout)…" (stream right-click, or the call window's Media tab) turns a bare "jitter = N ms" into "how much audio would actually be lost." A receiver's de-jitter buffer holds each packet until its scheduled playout instant; a packet that arrives later than that is discarded and played as concealment/silence. The tool runs the captured arrival timing through buffers of several depths (10–200 ms) and shows the estimated discard % at each, plus the smallest buffer that keeps discard under 0.5%. When even the deepest buffer can't — the delay variation is too severe to hide, so expect audible loss no matter the buffer. It's pure timing math (no audio decode), and it estimates what the receiver's RTCP-XR discard% would report when the far end doesn't send XR. Deeper buffers cost mouth-to-ear delay, so the smallest adequate depth is best.

Scanning for in-band DTMF

Most DTMF is carried out-of-band as RFC 4733 telephone-events and is decoded during analysis (the DTMF column). When digits are instead sent as audio TONES in the media, right-click → "Scan for in-band DTMF (decodes audio)". Because decoding audio for every stream in a large capture would be ruinous, this is on-demand: it decodes just the stream you picked, runs tone detection, and lists each digit with its time and duration. The same scan is on the Calls tab ("Scan media for in-band DTMF") for a whole call's streams.

Graphs tab

What it is

Charts trends across the whole capture. You choose a METRIC (what to measure), a HORIZONTAL axis (usually Time, or a category), an optional GROUPING (a colored series per group), and an optional PANEL split (a separate small chart per group).

Building a graph — the controls

  • Horizontal — Time (a time series) or a category (a bar per group).
  • Metric — the quantity being measured. See "Graph metrics reference" for every one.
  • Group / series — draw one colored line/area per group (per media source, per codec, per protocol, per HTTP host…). "No grouping" is a single series.
  • Panels — split into a grid of small charts, one per group, instead of one busy chart.
  • Y per panel — each panel scales to its OWN peak instead of the shared maximum, so one loud device can't crush every other panel into a flatline. Read values off each panel's own axis labels; percent metrics stay anchored at 100.
  • Bucket — the time-slice width for time-axis metrics (finer = more detail, coarser = smoother).
  • Top N — keep only the N most significant groups (the rest are dropped or pooled).
  • Order — which groups win the Top N and the drawing order: Worst/Best first for quality metrics, Biggest/Smallest for volume metrics, or by name. The labels change to match the metric because "worst" MOS is the LOWEST, not the highest.
  • From / To — restrict to a time range.
  • Style — Line, Area, or 3D bars.

Limiting every graph to a subnet

The Subnet box on the second toolbar row limits EVERY graph on this tab to traffic touching a subnet or address — type 10.90.216.0/22 and press Enter. It takes src: / dst: for one end, ! to exclude, a plain address for one host, and several at once separated by spaces or commas (all must hold). The box turns yellow while it is on, and the graph title shows the filter, so a screenshot pasted into a ticket still says what it was limited to.

What "touching" means depends on what the graph counts, and each is the natural reading:

  • call graphs (calls started, concurrent calls, ASR, PDD...) count a call when any of its legs' SIP addresses OR its media addresses are inside
  • stream graphs (loss, jitter, MOS, RTP packets...) count a stream by its OWN two addresses — so a site's loss graph does not pick up the carrier-side stream of a call that merely had a phone at the site
  • packet and HTTP graphs count each packet or request by its own two addresses
  • SIP retransmissions follow their call when they belong to one, and their own two addresses when they do not (an OPTIONS keepalive, a stray BYE)

Clicking a spike honours it too: the calls it offers are the filtered calls, and a packet graph opens the Packets tab with the same subnet already in its Address box.

The Filters... dialog is a different filter: it hides VALUES of a call or stream grouping (a cause, a codec, one IP), so it only reaches call and stream graphs — packet, HTTP and duplicate-packet graphs have no call to test. The two combine.

Saved reports

The report dropdown holds named, reusable graph configurations that persist across sessions and apply to any capture. A starter set ships with the app (call volume, ASR, post-dial delay, MOS/loss/jitter by media source, lossy media paths, throughput by protocol, SIP retransmissions, HTTP status/response/error). Save your own, and "Restore common reports" brings the starters back.

3D bar mode

  • Height and a base→top color gradient both encode value, so you can estimate bar height even looking straight down.
  • Mouse: LEFT button drags/slides the scene, RIGHT button rotates/orbits.
  • Row/column titles stay parallel to their rows and rotate when columns get crowded, to keep labels from overlapping.

The ? button

The ? next to the controls opens "Graph metrics reference" and "Graph groupings reference" — every metric and grouping explained.

Clicking a spike → the calls behind it

On a time chart, click a point (the tooltip says "click here to open this call") to open the calls that produced that value. When several contribute, a list pops up at the cursor ranked by each call's own contribution — for a latency spike, the highest-latency calls first (with their ms); for loss, the calls that lost the most packets there; for MOS, the worst first. Calls that merely started in that second but carry no measurement for the metric are left out, so the top of the list is the real cause. One contributor opens directly. In Panels mode the click is scoped to the panel strip under the mouse — a spike in one panel never picks a point from another, and the hover popup describes only the panel you are over.

Panel titles are clickable

  • LEFT-click a panel's title (the IP/host/codec naming it) to open that value SOLO as a single full-size graph. A "solo: X ✕" link appears next to the Filters button — click it to return to the panel grid you came from.
  • RIGHT-click a title for more: open solo, find all CALLS to/from that value (jumps to the Calls tab searched for it), find all LEGS (Legs tab), or copy the name.

The * span marker

A panel title ending in "*" marks an address the capture sees WHOLE: it converses with many distinct peers (10+), which is the signature of a SPAN/mirror target (the CUBE, a proxy) rather than an endpoint that happens to cross the capture point. Hover the title for the peer count. Quality numbers for a spanned address aggregate EVERYONE it talks to — rank the far-end panels to find which conversations actually hurt.

Empty buckets are gaps, not zeros

Average metrics (MOS, jitter, latency) leave buckets with NO calls as a gap in the line rather than plotting a fake 0 — an idle minute is not a MOS-0 minute. Rate metrics still draw honest zeros.

The tabs

Endpoints tab

What it is

One row per IP address that appears anywhere in the session — as a SIP leg end or an RTP stream end. Every number on the row is that address's total, so this is the "who are the players and how are they behaving" view.

Calls 0 with media on the row

Calls counts the calls this endpoint is a SIP PARTY to — one end of a leg. A desk phone registered to CUCM never signals to a CUBE, so on a capture taken AT the CUBE its row reads 0 calls and non-zero "Media calls": CUCM did the signalling (sme-ucm-sub1b → sme-cube-1a) while the phone's own RTP went straight to the gateway and was captured. Every quality number on that row is real; only the signalling is somebody else's. Carrier SBCs split the two deliberately for the same reason. Both columns 0 with streams present is the different case: media whose signalling was never captured at all.

What you see first

The tab opens on the WORST AUDIT IT SENT: sorted by Imperfect audio out % descending, so the device everyone else is hearing break up is the top row before you touch anything. The header carries a ▼ to say so — a filled mark is the column being sorted on, a hollow one the layer under it (sorting by a second column keeps the first as a tie-break).

About twenty of the fifty-odd columns are on by default — who (address, hostname, SIP user, carrier), how much (calls, media calls, the busiest instant, failures), and how it SOUNDED going out, which is the direction this endpoint is answerable for. Actual loss-out % and Imperfect audio out % sit side by side on purpose: they are two different facts and the pair of them is the summary — "80% of the call had 3.5% audio loss". Right-click any header for the rest; hovering an entry there explains what it means before you switch it on.

What it answers

  • Which carrier/org owns a public endpoint (whois columns).
  • How many legs it originated vs received, streams it sent vs received.
  • Its loss/jitter/MOS, both unweighted (per-stream average) and packet-weighted (Actual loss %) so one tiny lossy stream can't skew the verdict.
  • Bad-audio calls — distinct calls where media this endpoint RECEIVED actually broke up.
  • Bad-audio legs in / out — the same verdict scoped to LEGS (a stream is one leg's portion of one call, so a user whose short leg sits inside a long call still counts), and split by direction. "Out" is the one that catches a phone on a bad connection: its received columns read clean while everyone ELSE hears it breaking up — that bad audio otherwise lands on the gateway's row and drowns.
  • What it SENT: Actual loss-out % (what it sent that never reached the capture point — a phone on a bad connection shows here while its loss-in reads clean), Bad audio s out (seconds everyone else spent hearing this device break up), Avg/Min MOS out (the quality of the audio it PRODUCES — the received-side MOS of a phone on a bad connection reads a clean 4.4, because nothing is wrong with what IT hears), and RTCP loss-out % / RTCP lost out — the receivers' own verdict about media from this IP.
  • L events out / in / total — how many times its audio went missing and came back, each way and both together, with per-minute rates. One long hold/MOH gap is ONE event; a phone dropping packets all through its calls is hundreds. Every gap of at least the Settings "loss event minimum" counts (default 1 lost packet); silence suppression does not. Sort by L events total or L ev/min total to catch a bad endpoint whichever direction its audio breaks up.
  • Imperfect audio in / out / % — the share of its audio seconds with a dropout in them (TIME affected, not packets lost). Only seconds in which packets arrived count as audio, and a long gap is never a dropout second, so hold music, one-way stretches and dead air cannot make an endpoint look broken.
  • Worst dropout loss-in / -out % — the other half of that: of the seconds that WERE affected, how much went missing, on the worst single stream. The pair finds two different kinds of bad endpoint, and one column alone finds only one of them: a device that is continuously slightly broken reads high imperfect and low dropout loss, while one that tore hard for four seconds reads low imperfect and high dropout loss — the second is invisible in every loss column, because four bad seconds in a day average away to nothing. Worst, not pooled, for that reason. Phantom one-way audio cannot reach these columns: silence is not audio.
  • RTCP direction, spelled out: RTCP loss-OUT % and RTCP lost out = other endpoints' reports accusing THIS endpoint's media. RTCP loss-IN % and RTCP lost in = THIS endpoint's own reports complaining about the audio it received — the only witness to loss between the capture point and the endpoint. High in both = a genuinely bad path. Blank = no report this capture can measure, never "clean".
  • MOS comes in TWO witnesses per direction. Capture-based (Avg/Min MOS, Avg/Min MOS out) scores the audio AT THE CAPTURE POINT — it cannot see the last mile. RTCP-based (Avg/Min MOS in/out (RTCP)) is built from receiver reports: "in (RTCP)" from the endpoint's OWN reports (sees loss between the capture and the endpoint), "out (RTCP)" from its listeners' reports. Capture MOS-in 4.4 with a low MOS in (RTCP) = the audio left the capture point clean and died on the way to the phone. RTCP can be fabricated and counts hold/re-points as loss — check the divergence verdicts.
  • "vertical headers" (checkbox) rotates the column headers 90° and narrows the numeric columns — header names stop deciding column widths, so far more columns fit on screen.
  • User (SIP) — the person whose MEDIA lives at this IP. Each name is taken from a SIP message that asserted an identity (RPID/P-Asserted-Identity, or From on the initial INVITE) while that same message's SDP advertised this media address — the re-INVITE that delivers a call to an agent both names the agent and points media at their phone. ONE name = that user's phone. A FEW names = a shared phone / extension mobility / hot desking. MANY names = a gateway/B2BUA media address relaying other people's calls, not a person — and identities can swap per call, so treat it as a strong hint, never proof. The endpoints CSV carries the full name breakdown with counts.
  • Max concurrent calls — the busiest INSTANT, which is the capacity number. Calls counts the whole capture (a gateway reads thousands over a day while it never carried thirty at once); this counts how many were live at the same moment. Each call is counted over its own lifetime, the same interval the Concurrent calls graph draws, and an endpoint qualifies through a SIP leg or through media alone — so a phone that only ever appears in the RTP still counts. A call that reaches the endpoint on two legs counts once, and calls that merely touch — one ending as the next starts — are not concurrent. The endpoints CSV also carries when the peak began (UTC).
  • DSCP in vs out — compare across endpoints to see where QoS marks get stripped.

"Streams but no calls?"

Carrier SBCs frequently split SIGNALING and MEDIA across different addresses. The Calls column counts SIP-signaling legs; a pure media address carries hundreds of calls' RTP while its Calls reads 0. That is why there is a separate MEDIA CALLS column — distinct calls whose RTP touches the endpoint. If BOTH are 0 while streams are present, it is media whose signaling was never captured at all.

Drilling down: endpoint → stream → call

DOUBLE-CLICK an endpoint to open the RTP Streams tab filtered to it — every stream it sent or received. Double-click one of those streams to open the call that stream belongs to (a stream with no SIP setup captured opens the audio player instead). That is the natural path for a media story: which of this phone's streams is bad, then which call it was.

The Imperfect audio % cells are SHADED so a bad device shows up before you sort anything: yellow from 5%, amber from 20%, red from 50%. A blank cell (under 10 seconds of audio, nothing to rate) stays plain — it must not read as "clean".

Actions (right-click)

  • Show this endpoint's RTP streams (the same as double-clicking).
  • View this endpoint's AUDIO HISTORY — every conversation it took part in, laid back to back with the idle time removed, with the loss/jitter overlay, the RTCP loss marks and playback. It opens on the audio the endpoint SENT — what everyone else heard from it, and the side this capture can judge for itself, since those packets arrived here so their gaps are real (the RTCP marks on those lanes are its LISTENERS' reports). A combo switches to the audio it was sent — what its user heard, where the RTCP marks are its own — or both. The axis clock still shows the real time of each piece, so it jumps at every conversation boundary.
  • Graph this endpoint over time — loss, audible loss, loss bursts, jitter, MOS, packets or throughput, on the Graphs tab with the address filter already applied. The Metric combo switches between them; clear the Subnet box to go back to the whole capture.
  • Search calls involving this endpoint; filter the Packets or SIP tab to this IP; copy the IP or its carrier/org name.

Networks tab

What it is

The Endpoints tab one level up: one row per NETWORK LOCATION instead of per address, with every column summed over the addresses inside it. A branch office whose twelve phones each look mildly lossy is ONE row here, and it reads badly — which is the point. A carrier's whole media range collapses from two hundred rows into one.

How addresses become networks (the "Group by" combo)

  • Settings rules, then /24 (the default once you have written any rules) — your own network rules name what they cover (Settings → network rules, e.g. 10.92.0.0/16=PSTN), and every address no rule names falls back to its own /24.
  • Settings network rules only — one row per label, plus a single "(no network rule)" row holding everything unnamed. Use it to see how much of the capture your rules still miss.
  • Assume /24 (255.255.255.0) — the default when there are no rules at all. It is a GUESS: a capture does not carry subnet masks, so nothing here can prove where one network ends. On a LAN a /24 per site is right far more often than not, which is exactly why it is offered — as a starting point, not a fact.
  • Assume /16 (255.255.0.0) — one step wider, for a campus whose /24s split one location.

IPv6 addresses group by /64 (or /48 for the wider choice).

Naming your networks in Settings turns the guesses into real answers, and the labels then show up here, on the Legs/Streams/Endpoints "Network" columns, and as graph groupings.

What it answers

  • Which SITE is having a bad day — sort by Imperfect audio %, L ev/min total, Actual loss-out % or Bad-audio legs out. The cells are shaded the same way as on Endpoints (yellow from 5%, amber from 20%, red from 50%; a blank cell means under 10 seconds of audio, nothing to rate).
  • Whether a problem is one phone or the whole subnet: if the network row looks bad, drill in and see whether every endpoint inside it does.
  • How many addresses each location actually has (Endpoints column), and which they are (Addresses column, and the full list in the networks CSV).
  • How busy the site gets: Max concurrent calls is the peak over ALL its addresses at once, which is the number a site's trunk or bandwidth has to carry — not the per-phone peak.

Reading a row

Every column means exactly what it means on the Endpoints tab — they are computed by the same code, just over a set of addresses. Two consequences worth knowing:

  • Calls, Media calls and the bad-audio counts are DISTINCT counts, so a call with both ends inside one network counts once, not twice.
  • Streams out and Streams in both count a stream whose two ends are inside the SAME network — from the network's own point of view it did send it and did receive it.

Drilling down

  • DOUBLE-CLICK a row (or right-click → Show this network's endpoints) for the Endpoints tab showing exactly that network's addresses. The filter NAMES itself in the Endpoints Find box — a subnet as its CIDR, a rule- or carrier-named network under its own name — so the tab can never be quietly filtered without saying so. Click the box's ✕ to clear it and get every endpoint back; type over it to replace the drill-down with your own filter. Pressing Enter on the name unchanged simply re-applies it.
  • Right-click also offers this network's RTP streams, its calls, the Packets tab filtered to it, and "Graph this network over time" (loss, audible loss, loss bursts, jitter, MOS, packets, throughput, RTCP-reported loss).
  • Those filter-by-subnet actions need ONE subnet to work with. A Settings rule that covers several CIDRs has none, so they are greyed out on that row and say why — open its endpoints and drill from there.

Exporting

Export → Networks (.csv) writes the current grouping: the network, the grouping used, its subnet, how many addresses and which, then the same metric columns as the endpoints CSV. The CLI has it too: `vsx analyze <files> --networks-csv net.csv [--group-by rules|rules24|24|16]`.

Registrations tab

What it is

One row per REGISTER transaction in the capture — every attempt by a phone, soft client, or gateway to register (or de-register) with a registrar. This is where you answer "are endpoints registering, and are any being rejected?"

How a REGISTER is read

VoipStudio pairs each REGISTER request with its transaction's final response and classifies the outcome:

  • Registered — accepted, a new binding (expires > 0).
  • Refreshed — accepted, a periodic refresh of a binding already seen.
  • Deregistered — an unbind (the client asked for expires 0) that succeeded. Rows shown in gold.
  • Rejected — a 4xx/6xx final: 403 Forbidden (bad credentials/policy), 404 (unknown AoR), 423 Interval Too Brief, 486, 603… Rows shown in red.
  • Server error — a 5xx: the registrar failed, not the client. Red.
  • Auth challenge — a 401/407 with no captured authenticated retry that completed. Red.
  • Unanswered — the REGISTER got no final response at all. Red.

The normal 401 → re-REGISTER-with-credentials → 200 handshake is recognized: only the final 200 shows as the outcome, and the intermediate 401 is marked as a superseded auth step so it never inflates the failure counts.

Finding failures fast

  • Tick "Problems only" to hide the healthy registrations and keep just rejects, server errors, unresolved auth challenges, and unanswered attempts.
  • The count line summarizes the whole capture: how many registered / refreshed / deregistered / rejected / server-error / unresolved-auth / unanswered, across how many AoRs and registrars.
  • Sort by any column (Outcome, Status, AoR, Latency ms…). Latency ms exposes a slow or overloaded registrar.

The columns

AoR (the identity), Client (the device), Registrar (the server), Outcome, Status, requested vs granted expiry (a granted expiry shorter than requested means the phone must re-register more often), latency, User-Agent, and the Contact binding. Hover any header for its full definition.

Actions (right-click)

Filter the SIP tab to this Call-ID (to read the actual messages), filter the Packets tab to the client↔registrar conversation, or copy the AoR, ip:port, or a Wireshark filter. Export everything via toolbar Export → Registrations (.csv); a registration summary also appears in the session summary text export.

Registration problems that recur for one AoR (a phone that rejects then retries in a loop, or keeps going unanswered) are a classic root cause of "my phone randomly drops" — sort by AoR with Problems-only on to see the pattern.

Keepalives tab

What it is

Two kinds of non-call SIP signaling that never appear on the Calls tab but are where a lot of "why did the phones/trunk misbehave" answers live:

  • OPTIONS keepalives (top grid) — the heartbeat SBCs/trunks/phones use for dead-peer detection.
  • SUBSCRIBE/NOTIFY subscriptions (bottom grid) — presence/BLF, voicemail MWI, and dialog event packages.

Tick "Problems only" to hide the healthy ones in both grids at once.

OPTIONS keepalives

A device proves its peer is alive by sending SIP OPTIONS on a steady cadence and expecting a response. One row per pinger→target relationship, with a Health verdict:

  • healthy — every OPTIONS answered on a steady beat.
  • cadence gaps — the heartbeat paused far longer than its interval (missed pings — a failover, the pinger's own trouble, or a capture gap).
  • errors — the target answered non-2xx (e.g. 503 Service Unavailable = signaling out-of-service).
  • flapping — some OPTIONS went unanswered; the target dropped intermittently.
  • DOWN — no OPTIONS was ever answered; the target is unreachable.

Only SILENCE means dead — a 405/503 still proves the peer is reachable. The Interval and Longest-gap columns show the cadence and its worst interruption. This is the fastest way to answer "did that SIP trunk flap, and when?".

SUBSCRIBE / NOTIFY subscriptions

One row per subscription dialog: the watched Resource, the Subscriber and Notifier, the Event package (presence / dialog=BLF / message-summary=MWI / refer…), and the Result:

  • Active — accepted (2xx), subscription up.
  • Pending — 202 accepted, authorization pending.
  • Rejected (code) — 4xx/6xx (403 Forbidden, 404, 489 Bad Event…). A wall of rejected presence/BLF subscriptions is a classic "the lamps don't light" cause.
  • Terminated (reason) — a NOTIFY ended it; deactivated/probation/rejected/giveup/noresource are the bad reasons (a plain timeout after a healthy run is normal).
  • Unsubscribed — the watcher ended it on purpose (Expires: 0).

Actions & export

Right-click either grid to filter the SIP or Packets tab to that peer/dialog, or copy it. Export → "OPTIONS keepalives (.csv)" and "Subscriptions (.csv)"; both also appear in the session-summary text export. Hover any column header for its full definition.

These run during normal analysis (pure signaling — no audio decode), so they're always populated when the capture carries OPTIONS or SUBSCRIBE traffic. A pure trunk capture may have OPTIONS but no subscriptions; a phone-side capture usually has both.

Skinny tab

What it is

Cisco phones that don't use SIP speak SCCP ("Skinny") — a binary station-control protocol to the CallManager over TCP (default port 2000). This tab decodes that traffic so those phones' registrations and calls become visible; without it they're just opaque TCP.

It only populates when the capture carries SCCP. A pure SIP/trunk capture shows nothing here. The SCCP port is configurable in Settings.

Registrations / sessions (top)

One row per phone↔CallManager control connection: the phone and CallManager addresses, the device name (e.g. SEP001122334455) and type, and a status — registered, REGISTER REJECTED (in red), unregistered, or active — plus how many calls and messages it carried.

Skinny calls (bottom)

One row per call, tied together by its Skinny call reference: calling and called parties (from CallInfo), call type (inbound/outbound/forward), the final call state (OffHook→Proceed→Connected→OnHook…), dialed digits, the negotiated codec, and the RTP media endpoints the CallManager set up — the phone's own receive ip:port and the remote ip:port it transmits to. Graph metrics reference

Call volume & outcome

  • Calls started /s — new call attempts (first INVITEs) per second. The offered-load curve; group by cause to see failure spikes.
  • Concurrent calls — how many calls are simultaneously up. The capacity / busy-hour view.
  • ASR % (answered/attempts) — Answer-Seizure Ratio: the share of attempts that answered. The headline completion metric; HIGH is good.
  • ACD — avg talk time (s) — Average Call Duration of answered calls.

Setup timing (milliseconds)

  • Post-dial delay (ms) — INVITE to ring/answer; how long the caller waited hearing nothing. Slow routing shows here.
  • SIP: INVITE → 100 Trying — far-end transport round-trip + initial processing.
  • SIP: INVITE → 18x ringing — time to the first 180/183; how long routing took before alerting.
  • SIP: INVITE → final response — to the first 200 OK or failure (includes human answer time for answered calls).
  • SIP: 200 OK → ACK — answer to the caller's ACK; large values mean a slow caller-side device or path.

Audio quality

  • Average MOS — estimated voice quality 1–5 (E-model). HIGH is good; below ~3.5 draws complaints. See "MOS & the E-model".
  • Packet loss % (capture-observed) — loss from RTP sequence gaps AT the capture point.
  • Packet loss % (RTCP receiver-reported) — loss the far-end RECEIVER reported. Compare with the capture number to locate loss (see "Packet loss explained").
  • Audible loss % — loss counting only short bursts, excluding hold/MOH gaps: what a listener actually heard. The one to trust for "bad audio."
  • Loss bursts /s — runs of consecutive lost packets per second. 1 = a single gap (hold/re-route); many = audio breaking up repeatedly.
  • RTP jitter (ms) — mean RFC 3550 interarrival jitter. Above ~30 ms strains jitter buffers, above ~60 ms is usually audible.
  • RTCP lost packets /s — packets the far-end RECEIVERS said went missing (cumulative-lost deltas from their receiver reports), charged to the MEDIA SENDER whose packets they were. Late arrivals that "un-lose" packets are never re-counted. Group by Media Source IP to rank which senders' media is dying en route — independent of where the capture sits.
  • RTCP loss complaints /s — how often receivers filed a report claiming NEW loss, charged to the REPORTING endpoint (so Media-Source/Destination groupings swap sides: the series names are the complainers). Many complaints from one endpoint = that endpoint's inbound path hurts; one sender charged by many reporters (see the lost metric) = the sender's side hurts. Beware fabricated RTCP from middleboxes.

Traffic & signaling health

  • RTP packets /s — media packet rate.
  • SIP INVITEs /s (initial) — NEW call attempts per interval, retransmissions and re-INVITEs excluded. The calls-per-second number carriers and licenses cap; graph it before blaming a carrier for rejecting bursts.
  • SIP retransmissions /s — re-sent SIP transactions; packet loss or unresponsive peers on the signaling path.
  • Duplicate packets /s — SPAN mirror duplicates per second (a capture-quality metric, not a network fault).
  • Packets /s (all protocols) — total captured packet rate.
  • Throughput (KB/s captured) — captured bytes/sec. Group by Protocol or Port to see where bandwidth goes.

HTTP (needs HTTP decoding enabled)

  • HTTP requests /s — request rate; group by status class to see error waves.
  • HTTP response time (ms) — server think-time (request → response); group by host.
  • HTTP error % (status ≥ 400) — share of responses that were errors.

On a categorical (non-time) horizontal axis these same metrics read as counts/totals per category — e.g. "Calls (count)" instead of "Calls started /s."

A grouping turns one metric into several — one colored line/area (as a Series) or one small chart (as a Panel) per group value. Pick the dimension you want to compare across.

  • Import Hosts file — "ip hostname" per line (# comments). The most reliable naming, re-applied after every analysis.
  • Whois for public IPs (RDAP) — fills carrier/org columns; needs internet; cached to disk forever.
  • Reverse DNS for LAN/private IPs (PTR) — asks your DNS server; cached to disk.

Correlation tolerances (re-analysis required)

These control how separate SIP dialogs get joined into one call. Defaults suit most Cisco/CUBE designs; widen them for slow gateways, tighten them if unrelated calls merge.

  • B2BUA chain window (s) — max gap from an incoming INVITE to its outbound leg for the two to be chained into one call.
  • Rare-number floor (legs) — a caller number seen at or below this many legs is always treated as "rare" (customers call back a few times), which lets it tie legs together across number translation.
  • Rare-number ceiling (% of legs) — above the floor, "rare" means the number is at most this share of ALL legs, so the definition scales with corpus size.
  • Transfer end-sync tolerance (s) — a delayed queue/agent leg joins its call when both legs END within this window.
  • Transfer window grace (s) — how long after a REFER the transferred INVITE may arrive and still be linked.
  • Related-call adjacency (s) — max gap between the starts of related calls (transfers/loopbacks) for them to be marked related.

Capture cleanup

  • Duplicate window (ms) + Enable duplicate-packet removal — SPAN taps often mirror both ingress and egress, so each packet appears twice. Copies within this window are dropped so counts and loss aren't doubled. Set the window to 0 or disable only if you are sure there is no mirroring.

Bad-audio / bad-call thresholds

These define what the Bad Calls tab, the endpoints "bad-audio" columns, and Poor Audio s count as bad:

  • Poor-audio threshold (audible loss %) — above this, audio is classified CHOPPY.
  • Poor-audio floor (lost packets) — AND at least this many audible lost packets, so a single dropped packet in a tiny prompt doesn't register.
  • Bad-call jitter threshold (ms) — mean jitter above this fires the jitter symptom.
  • Bad-call MOS floor — MOS below this fires the low-MOS symptom.
  • Choppy audio: imperfect audio at least (%) — what share of a stream's audio SECONDS had a dropout in them, for the Bad Calls "choppy audio" symptom and the red rows on the Calls tab. Default 25%.
  • Choppy audio: actual loss at least (%) — AND at least this much really missing, with hold/MOH and silence-suppression gaps excluded. Default 3%. BOTH must be met: a steady 3% loss touching 80% of the seconds is broken audio, the same 3% inside two seconds is one blip, and 80% of the seconds touched at 0.1% loss is a codec dropping the odd packet.
  • Loss event minimum (lost packets) — how many lost packets in a row make one L EVENT, and make a second of audio count toward Imperfect audio %, on the Calls, Legs, RTP Streams, Endpoints and Bad Calls tabs and in the CSV exports. 1 (the default) counts every dropped packet; raise it to ignore single-packet blips. Applies immediately — no re-analysis.

Ports (re-analysis required)

Comma-separated lists; ranges allowed (e.g. "5060-5091, 5094"). These tell the classifier which ports carry which protocol:

  • SIP ports — plaintext SIP signaling; default 5060-5091.
  • SIP-TLS ports — encrypted SIP; routed to the TLS inspector; default 5061.
  • HTTP ports — plaintext HTTP to decode (with HTTP decoding on).
  • HTTPS ports — TLS-classified and handshake-inspected; default 443. HTTPS never reaches the plaintext HTTP decoder.

Optional decoders (re-analysis required)

  • Decode HTTP traffic — populates the HTTP tab and HTTP response graphs. Off by default; turn on when you care about phone provisioning / web-service traffic.
  • Reassemble T.38 fax (UDPTL/T.30) — the heaviest optional step; enable only when analyzing fax.

Memory — disk-streaming (low-memory) mode

Controls where the large per-packet index and RTP data live:

  • Auto (default) — kept in RAM, but spilled to disk automatically when a capture is large relative to THIS machine's memory (the same point the lean index engages).
  • Always on — always spill, for weak PCs / little RAM.
  • Off — always keep everything in RAM (fastest, needs the most memory).

When on, those big data blocks are memory-mapped to temp files instead of the managed heap, so the resident set stays small and a capture much bigger than RAM can open — the OS pages the data in and out on demand. It is slower than pure RAM (disk seeks), and the analysis results are exactly the same either way. Temp files are deleted when you close the capture. On a sample capture this cut the in-RAM footprint by about 40% with byte-identical results.

If a tab or column is unexpectedly empty, the cause is almost always here: HTTP decoding off, the relevant port not in its list, or whois/rDNS disabled. Change the setting and re-analyze.

Packet loss explained

Three different "loss" numbers, and why they differ

VoipStudio reports loss more than one way ON PURPOSE, because where you capture changes what you see.

  • Capture-observed loss — gaps in RTP sequence numbers AT the capture point (your SPAN). This is loss BEFORE the packets reached your tap. Loss that happens downstream of the tap, toward the receiver, is invisible here.
  • RTCP receiver-reported loss — the far-end RECEIVER's own count, carried in its RTCP reports. This is the receiver's real experience, wherever the loss happened. A report that a flow-through B2BUA relays onto the next hop is counted ONCE, at its author's hop. The relayed copy is still listed, marked relayed, in the Packets grid, the call Timeline and the Call Flow's RTCP view.
  • Audible loss — capture loss counting only SHORT bursts (≤ ~1 s), with long continuous gaps excluded. This is the choppiness a person actually hears.

The divergence verdict (RTP vs RTCP)

Comparing capture loss with RTCP loss LOCATES the loss:

  • consistent — both agree.
  • RTCP loss / capture clean — the capture is clean but the receiver lost packets: loss is DOWNSTREAM of your tap (between tap and receiver).
  • capture loss / RTCP clean — you saw gaps the receiver didn't: packets bypassed your tap (a SPAN gap), not a real network loss.
  • both report loss — loss is UPSTREAM of the tap (before it), and reaches the receiver.

Real loss vs math loss (the Loss Bursts trick)

A call on hold, playing MOH, or re-routing media keeps counting RTP sequence numbers across a gap, which looks like huge "loss" but nobody heard anything. The tell is BURST COUNT: ONE big burst is almost always such a benign gap; DOZENS of small bursts is audio that genuinely broke up. That is why Audible Loss % (short bursts only) and Loss Bursts exist — sort by them, not by raw Loss %, to find calls a caller complained about.

L events and imperfect audio

An L EVENT is one time the audio went missing and came back: a gap of at least the Settings "loss event minimum" (default 1 lost packet). Five hundred packets lost in one hold gap is one event; five hundred lost a packet or two at a time between received packets is hundreds. Gaps where the sender simply stopped sending during silence (VAD/DTX — its media clock froze) are not events, because nothing was lost.

IMPERFECT AUDIO % turns that into a share of TIME: of the seconds that carried audio (seconds in which packets arrived), how many were not perfect — how many had at least one short L event in them. Silence — hold/MOH, a one-way stretch, dead air — is not audio time, and a long gap is never a dropout second, so ten seconds of silence can neither read as ten broken seconds nor water down the real dropouts around them. It is measured per stream, per leg and direction, and per endpoint; the Calls tab shows the WORST leg, direction and device, so a bad agent leg is not diluted by a long IVR leg on the same call.

IT IS NOT A LOSS PERCENTAGE, and the two look very different on the same call. A phone that drops single packets steadily loses about 3% of its packets while touching about 85% of its seconds: "Loss %" answers how much audio went missing, "Imperfect audio %" answers how much of the time was affected. Raise the loss-event minimum to 2 and only the bigger gaps count, which is the quickest way to see whether the damage is scattered single packets or real bursts.

Every imperfect-audio percentage needs at least 10 seconds of audio behind it and is blank below that: one dropout in a 4-second ringback stub would otherwise read 25%. The Calls tab's worst-leg figure is also blank for a call that never connected (failed or cancelled with no leg answered) — ringback or an announcement on an attempt is not a conversation.

Sequence jumps of a few thousand are treated as stream RESTARTS (prompt replays, device restarts), not loss, so a re-used SSRC doesn't read as a catastrophic drop.

MOS & the E-model

What MOS means here

MOS (Mean Opinion Score, 1–5) is an ESTIMATE of voice quality. VoipStudio computes it from the ITU E-model (G.107): it builds an R-factor from the codec, the AUDIBLE loss, and the jitter, then maps R to a MOS. Rules of thumb: 4.4 is perfect G.711, ~4.0 is good, below ~3.5 is where users start to complain, below 3.0 is bad.

Why it uses AUDIBLE loss

If MOS were driven by raw sequence-gap loss, every call that sat on hold would score terribly. By feeding the E-model burst-adjusted (audible) loss, a hold/MOH gap doesn't drag the score down — so a low MOS here means audio that a listener would actually judge poor. Genuinely unexplained dead air is flagged separately (Notes / Bad Calls) rather than being folded into MOS.

It is an estimate, not a verdict

MOS is a model. Treat a low MOS as a strong POINTER — then confirm by opening the call and listening (the audio player) and by checking the loss/jitter columns and the RTP-vs-RTCP divergence. The number tells you where to look; your ears and the packets tell you what actually happened.

The E-model MOS reacts to loss and jitter, so it and the Bad Calls thresholds move together — if you retune the poor-audio/jitter thresholds in Settings, the calls that look "bad" change accordingly.

How calls are correlated

The problem

One phone call rarely equals one SIP dialog. A call through a CUBE/SBC has at least two Call-IDs (inbound leg + outbound leg); transfers, forking, and multiple gateway hops add more. VoipStudio joins these dialogs into ONE logical call so the Calls tab shows calls, not fragments.

How legs get joined (strongest to weakest)

  • Session-ID — RFC 7989 end-to-end Session-ID header matched across legs. A UUID half only counts when it is DISCRIMINATING (carried by at most 2 legs) — media/conference resources that stamp one UUID onto many legs are deliberately ignored.
  • Cisco-Guid — Cisco's per-call GUID, when the platforms propagate it.
  • Replaces / Referred-By — a transfer that explicitly names the dialog it replaces.
  • SSRC relay — the same media SSRC observed on both sides of a flow-through gateway.
  • B2BUA time-window chaining — an incoming INVITE and its outbound INVITE through the same gateway within the chain window, only when the pairing is ONE-TO-ONE.
  • Rare-number tie — a corpus-RARE number links legs even when the DNIS was translated between them.

What it is GOOD at

  • Anything with a protocol identifier: Session-ID, Cisco-Guid, Replaces. These joins are graded "protocol" in the call report's LEG CORRELATION EVIDENCE section and are essentially always right.
  • Quiet-to-moderate gateways where one INVITE in produces one INVITE out — the time window plus synchronized teardown chains these reliably.
  • Distinctive caller numbers: an ANI that appears on only two legs in the whole capture ties them across full digit translation.
  • Announced transfers (REFER / Replaces) — grouped into one call family with the parent.

What it is BAD at — and why

  • A REPEATING ANI on inbound calls. One customer redialing, a dialer, a carrier test number, or a masked/shared trunk ANI: once a number appears on many legs it stops being "rare" and the rare-number rule refuses it (by design — tying on a common number would weld unrelated calls together). Result: legs whose only link was that number stay SPLIT when the DNIS was translated between them. The floor/percent knobs in Settings decide where "rare" ends; loosening them trades splits for the worse failure, false merges.
  • Two simultaneous calls between the SAME numbers through the same gateway inside the chain window: the pairing is ambiguous, the one-to-one requirement refuses it, and both stay split. Deliberate — over-grouping poisons every downstream number.
  • Gateways that regenerate everything: new Call-ID, no Session-ID or GUID, translated numbers, transcoded media (no SSRC passthrough). There is nothing left to join on but timing, and on a busy system timing alone is ambiguous — expect splits.
  • One-sided captures: if the SPAN only sees one side of the gateway, the other leg was never captured. No rule can join what is not there (the call shows legs:1; searching "carrier legs:1 related" surfaces likely other halves seen elsewhere).
  • Parallel forks reusing a to-tag and session-timer-expiry teardowns still have rough edges in leg SPLITTING (one dialog mistaken for one leg).

How to see WHY a call joined (or did not)

  • Calls tab → Correlated By column; Legs tab → Joined By per leg.
  • The call's problem report has a LEG CORRELATION EVIDENCE section listing every join with its rule and a protocol-vs-heuristic grade — trust "protocol", verify "heuristic" on calls that matter.
  • Right-click a call → "Find related legs / combine" to inspect and manually merge.

What can be done

  • The single biggest fix is configuration, not tuning: enable RFC 7989 Session-ID end to end (on a CUBE: `session-id` under voice service voip → sip). Every heuristic join it replaces becomes a protocol join, immune to all of the above.
  • On all-Cisco paths, Cisco-Guid propagation gives a similar guarantee.
  • Capture at a vantage that sees BOTH legs of the gateway you care about.
  • Tune the Settings tolerances to the corpus: busy gateway → tighter B2BUA window; a corpus full of repeating ANIs → keep the rare-number percent strict; legs of one call splitting on a quiet system → widen the window slightly. Changes require re-analysis.
  • Over-grouping remains the failure mode the defaults are biased against: when in doubt the engine splits, because a wrong merge silently corrupts two calls' stats while a split is visible and repairable.

If a call looks mis-correlated, right-click it → "Find related legs / combine" to see and adjust exactly which dialogs belong together.

Live Monitor mode

What it is

Beyond analyzing saved captures, VoipStudio has a live Monitor mode that watches traffic as it is captured (via dumpcap) and triages calls in real time, raising alerts when calls go bad against dynamic thresholds.

Cross-stream loss-spike detection

Monitor mode watches for a network-wide loss EVENT: when many distinct active streams all lose packets in the SAME second, that is not one bad call — it is the network hiccuping under everyone at once. VoipStudio flags such spikes (and marks them RTCP-confirmed when receivers independently agree the loss was real) and records them to a network-events log that survives the monitor's rolling buffer budget.

Why it matters

A single mid-capture second where hundreds of streams all drop is the signature of a brief forwarding interruption (a reconvergence, a scheduled job, a link blip). Seeing it as ONE event — instead of hundreds of separately "bad" calls — points straight at the network rather than at any phone.

The same detection logic runs when reviewing a saved capture, so a loss spike that hit the whole capture is identified as a shared event rather than blamed on individual calls.

Glossary of terms

Telephony identity

  • ANI — Automatic Number Identification: the calling party number (SIP From).
  • DNIS — Dialed Number Identification Service: the called number (SIP To / request URI).
  • Asserted identity — the connected-line identity after transfer/retarget (Remote-Party-ID with an explicit party=calling/called tag).

Signaling

  • SIP — the call-control protocol (INVITE/BYE/etc.).
  • SDP — the media-offer body inside SIP messages (codecs, IP:port for RTP).
  • CSeq — SIP command sequence number + method; ties responses to requests.
  • B2BUA / CUBE / SBC — a back-to-back user agent (Cisco CUBE, a session border controller): terminates one call leg and originates another, so one call has multiple Call-IDs.
  • Q.850 — the ISDN cause-code standard SIP Reason headers use for disconnect causes.

Media

  • RTP — the real-time audio/video transport.
  • RTCP — RTP's companion control protocol; carries the RECEIVER's loss/jitter reports.
  • SSRC — the 32-bit synchronization source id tagging one RTP stream.
  • SRTP — encrypted RTP (shown with a lock symbol; payload not decodable).
  • DTMF — keypad digits. Usually carried out-of-band as RFC 4733 telephone-events (decoded during analysis, shown in the DTMF column). When instead sent as audio TONES in the media ("in-band"), right-click a stream or call → "Scan for in-band DTMF" decodes that audio on demand and finds them.
  • Jitter — variation in packet arrival timing (RFC 3550 interarrival jitter).
  • MOS — estimated Mean Opinion Score of voice quality, 1–5 (see "MOS & the E-model").

Network & capture

  • DSCP — the QoS marking in the IP header (EF/46 expected for voice, CS3/24 for signaling, BE/0 = unmarked).
  • SPAN — a switch port mirror; the usual capture source, and the reason packets can appear twice (see the dedup setting).
  • rDNS / PTR — reverse DNS, IP → hostname.
  • RDAP / whois — the lookup that names the carrier/org owning a public IP block.
  • JA3 — a fingerprint of a TLS client's handshake, identifying the client stack.

Tips & shortcuts

Fastest ways to work

  • Dark mode: the moon button on the toolbar switches every window immediately and is remembered.
  • Hover any column header for its full definition — every column is documented.
  • Press F1 on any tab for help about that tab; the Help toolbar button opens this manual at its table of contents.
  • Double-click a call or stream to open its detail.
  • Click a column header to sort; click again to reverse.
  • Right-click almost anything (call, stream, endpoint, packet, TLS/HTTP row) for context actions — cross-tab filters, copy, open detail, copy a Wireshark filter.
  • Drag capture files or a folder straight onto the window to analyze.
  • "New window" on the toolbar opens a second VoipStudio instance — load a different capture in each to compare two side by side.

Finding bad calls fast

  • Sort Calls (or Bad Calls) by Audible Loss % or Poor Audio s — these are the calls a listener actually suffered through, not hold/MOH math loss.
  • Sort by Min MOS ascending for the worst estimated quality.
  • On Endpoints, sort by Actual loss-in % (packet-weighted) or Bad-audio calls to find which side of the network is hurting.
  • On Graphs, use the "worst first" order with a Top N and group by Media path or Media Source IP to see WHERE loss concentrates, then right-click a spike to reach the calls.

When something looks empty or wrong

  • Empty HTTP tab → enable HTTP decoding (Settings) and set HTTP ports, then re-analyze.
  • Empty carrier/org names → enable whois; empty LAN names → import a hosts file or enable rDNS.
  • Unrelated calls merged, or one call split → adjust the correlation tolerances in Settings and re-analyze; use "Find related legs / combine" to inspect.

The whole app is read-only over your captures — you can click, filter, and export freely without ever changing the underlying data.
